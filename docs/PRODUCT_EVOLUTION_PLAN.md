# AgentHub 产品演进方案

## 1. 产品判断

AgentHub 不缺功能，当前核心问题是聊天、产物、执行、验证和部署之间缺少统一的产品对象。演进目标不是增加传统工作区，而是让一个会话自然承载一个持续目标，并让用户始终知道当前目标、最新产物、待决事项和下一步。

基本约束：

- 不删除现有功能，不拆分 Lite/Pro 两套产品。
- 一个会话代表一个持续目标，账户仍是当前最高隔离层级。
- 聊天是主入口，高级配置保留在设置中。
- Artifact 是可交付内容的权威来源，消息只负责解释和引用产物。
- 不记录或展示模型的原始思维链，只保留可审计的动作、结果和状态。

## 2. 目标产品模型

### 2.1 Conversation Goal Snapshot

每个会话保存一份轻量目标快照：

| 字段 | 含义 | 更新来源 |
| --- | --- | --- |
| `objective` | 当前持续目标 | 首条用户消息自动初始化，用户可编辑 |
| `stage` | `not_started/planning/building/validating/ready/blocked` | 系统与用户 |
| `latest_deliverable` | 最新可交付物名称 | Artifact 创建后自动更新 |
| `latest_artifact_id` | 最新 Artifact 版本 ID | Artifact 创建后自动更新 |
| `pending_decision` | 等待用户确认的关键决策 | Agent/HIL 或用户 |
| `next_action` | 明确的下一步 | Agent 或用户 |

它不是工作区，不包含文件树、成员、权限或独立导航。它只在聊天中提供连续任务所需的最小状态。

### 2.2 Artifact Authority

下一阶段将建立以下不变量：

1. 每次代码产出都创建不可变 Artifact 版本。
2. Canvas 通过明确的 `artifact_id` 加载，不再从 Markdown 代码块猜测当前代码。
3. 编辑后保存产生新版本，不覆盖历史版本。
4. 部署请求必须固定一个 Artifact 版本或 Bundle Manifest。
5. 质量评分、沙箱结果和部署记录都引用同一个 Artifact 版本。

多文件项目采用 Artifact Bundle/Manifest，而不是传统工作区：Manifest 记录入口文件及 `path -> artifact_version_id` 映射。现有单文件产物继续兼容，确认多文件交付需求后再启用 Bundle。

### 2.3 Readiness

产品明确区分三类状态：

- `Service Online`：数据库和 API 可用。
- `Model Connected`：当前租户已配置可用模型；否则为 Demo Mode。
- `Build Services Ready`：Redis 和部署 Worker 可用，可执行后台构建与发布。

聊天可以在 Demo Mode 下继续使用，但首次任务前必须明确提示当前不是实际模型执行。构建服务不可用不应让整个产品显示异常。

### 2.4 Execution Receipt

基于任务状态、工具事件、质量指标和部署日志生成可恢复执行回执。每次执行使用独立 `execution_id`，避免并发 Agent 的事件互相污染。回执只展示：

- 谁在何时执行了什么动作；
- 输入/输出摘要、耗时和成功状态；
- 产生或验证了哪个 Artifact 版本；
- 失败原因和可重试动作。

## 3. 分阶段实施

### 阶段一：任务连续性与真实状态

- 修复工具调用后用户目标丢失和并发事件流串扰。
- 统一 PM 的默认执行与关键决策提问策略。
- 增加 Goal Snapshot 数据、API 和聊天内编辑体验。
- 首条消息自动初始化目标。
- 增加三层就绪状态和首次任务预检。
- 完成迁移、租户隔离、API 和前端回归测试。

验收标准：旧会话无损升级；不同账户无法读写彼此目标；工具调用后模型仍拥有原始用户目标；用户不进入设置即可看懂当前运行能力。

### 阶段二：Artifact 成为权威源

- Artifact 增加稳定版本号、父版本和内容哈希。
- WebSocket `code` 事件携带 `artifact_id/version`。
- Canvas 优先恢复最新 Artifact，消息解析只作为旧数据兼容路径。
- 编辑、预览、质量验证都显式引用 Artifact 版本。
- 设计 Bundle Manifest，但仅在确认多文件交付需求后启用。

验收标准：刷新、切换会话或回滚版本后 Canvas 内容确定且可复现；消息中的旧代码不会覆盖用户选定版本。

### 阶段三：可复现部署

- 部署请求固定 `artifact_id` 或 `bundle_id`。
- Redis 只保存队列运行态，部署元数据和最终结果持久化到数据库。
- 会话内展示版本、验证结论、部署目标和日志下载。
- 保留现有设置页作为高级配置，常用发布动作从当前产物直接进入。

验收标准：同一版本重复部署输入一致；Redis 重启不丢失部署历史；用户能追溯线上结果来自哪个版本。

### 阶段四：执行回执与上下文动作

- 为一次用户请求生成 `execution_id`。
- 将 Agent 任务、工具调用、Artifact、质量验证和部署串成时间线。
- 在聊天及当前产物附近提供知识、验证、后台运行和部署动作。
- Benchmark 保持平台诊断定位，不与单个产物验收混合。

验收标准：中断后可恢复任务状态；失败可从明确步骤重试；不暴露原始思维链。

## 4. 暂不实施

- 组织、团队、RBAC 和成员邀请。
- 独立工作区、全量文件同步或桌面 IDE 模型。
- 微服务拆分、插件市场和完整事件溯源。
- 密码找回。

这些能力只有在账户级隔离、Artifact 权威和部署持久化稳定后，且出现真实用户需求时再评估。

## 5. 待产品验证问题

以下问题不阻塞阶段一：

1. 主要交付物是单文件页面，还是多文件可运行项目？这决定阶段二是否启用 Bundle Manifest。
2. Demo Mode 是长期保留的正式体验，还是仅用于首次试用？
3. 部署历史需要永久保存，还是允许用户设置保留期？
