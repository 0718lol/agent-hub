# 架构设计流程

适用场景：系统设计、技术选型、架构评审。

## 工作流程

### 第 1 步：需求分析

明确需求的各个方面：

1. **功能需求** — 系统需要做什么
2. **非功能需求**
   - 性能：QPS、响应时间、吞吐量
   - 可用性：SLA 要求
   - 可扩展性：用户量/数据量增长预期
   - 安全性：数据敏感级别、合规要求
3. **约束条件** — 预算、团队规模、时间限制、技术栈限制

### 第 2 步：方案设计

设计满足需求的技术方案：

1. **系统架构** — 整体结构和组件划分
2. **数据模型** — 核心数据结构和存储方案
3. **接口设计** — API 定义和通信协议
4. **技术选型** — 框架、库、中间件的选择

### 第 3 步：权衡分析

对关键决策进行权衡：

| 决策点 | 方案 A | 方案 B | 推荐 |
|--------|--------|--------|------|
| 数据库 | PostgreSQL | MongoDB | 根据数据结构选择 |
| 缓存 | Redis | Memcached | Redis 功能更丰富 |
| 消息队列 | RabbitMQ | Kafka | 根据吞吐量需求选择 |
| 部署方式 | Docker | K8s | 根据规模选择 |

## 常见架构模式

### 单体架构
- 适用：小型项目、团队小、快速迭代
- 优点：简单、部署方便
- 缺点：扩展困难、技术债务累积快

### 微服务架构
- 适用：大型项目、多团队协作、需要独立扩展
- 优点：独立部署、技术栈灵活
- 缺点：复杂度高、运维成本高

### 事件驱动架构
- 适用：高并发、异步处理、实时数据流
- 优点：松耦合、高吞吐
- 缺点：调试困难、数据一致性挑战

### Serverless 架构
- 适用：事件触发型业务、流量波动大
- 优点：免运维、按需付费
- 缺点：冷启动、调试困难、供应商锁定

## 技术选型决策框架

### 评估维度

1. **成熟度** — 生产环境验证程度
2. **社区活跃度** — 文档、Issue 响应、更新频率
3. **学习成本** — 团队上手难度
4. **生态系统** — 插件/扩展丰富程度
5. **长期维护** — 是否有大公司支持、是否持续更新
6. **许可证** — 是否符合项目要求

### 决策矩阵

对每个候选方案按维度打分（1-5 分），加权计算总分：

```
总分 = Σ(维度权重 × 维度得分)
```

选择总分最高的方案。
