# Git 冲突解决流程

适用场景：合并分支、rebase、cherry-pick 时遇到冲突。

## 工作流程

### 第 1 步：获取上下文

```bash
git status
git log --oneline -5
git diff --name-only
```

了解：
- 哪些文件有冲突
- 当前分支和目标分支的最近提交
- 冲突的类型（内容冲突、删除/修改冲突、添加/添加冲突）

### 第 2 步：分析冲突

对于每个冲突文件：

```bash
git diff <文件路径>
```

理解：
- HEAD（当前分支）的改动是什么
- 另一个分支的改动是什么
- 两者为什么冲突
- 正确的合并结果应该是什么

### 第 3 步：解决冲突

根据冲突类型选择策略：

#### 内容冲突（双方都修改了同一区域）
- 仔细阅读两边的改动
- 理解各自的意图
- 合并两边的改动，保留所有有效代码
- 如果两边改动逻辑矛盾，需要判断哪个是正确的

#### 删除/修改冲突（一方删除，一方修改）
- 确认删除是否合理
- 如果删除合理，接受删除
- 如果修改合理，保留修改并手动删除不需要的部分

#### 添加/添加冲突（双方都添加了类似内容）
- 比较两段内容
- 保留更完善或更正确的版本
- 如果都是有效的，合并两者

### 第 4 步：验证解决结果

```bash
# 检查冲突标记是否全部清除
grep -r "<<<<<<" <冲突文件>
# 应该没有结果

# 运行测试
npm test / pytest / 其他测试命令

# 检查代码是否能正常编译/运行
```

### 第 5 步：完成合并

```bash
git add <已解决的文件>
git commit  # 如果是 merge
git rebase --continue  # 如果是 rebase
git cherry-pick --continue  # 如果是 cherry-pick
```

## 常见冲突场景处理

### 同时修改了 package.json / requirements.txt
- 合并两个文件的依赖
- 运行 `npm install` / `pip install` 验证
- 检查依赖版本是否兼容

### 同时修改了数据库迁移文件
- 检查迁移顺序
- 确保迁移可以按顺序执行
- 如果有冲突的 schema 变更，需要创建新的迁移来合并

### 同时修改了配置文件
- 保留两边的配置项
- 检查是否有冲突的配置值
- 运行应用验证配置是否正确

### 同时修改了同一函数
- 理解两边对函数的修改意图
- 合并两边的改动
- 确保函数签名和行为兼容

## 高级技巧

### 使用 merge tool
```bash
git mergetool
```

### 查看冲突的共同祖先
```bash
git diff :1:<文件>  # 共同祖先版本
git diff :2:<文件>  # 当前分支版本
git diff :3:<文件>  # 另一个分支版本
```

### 临时搁置当前工作
```bash
git stash
# 处理其他事情
git stash pop
```

### 中止操作
```bash
git merge --abort    # 中止 merge
git rebase --abort   # 中止 rebase
git cherry-pick --abort  # 中止 cherry-pick
```

## 预防冲突的最佳实践

- 频繁从主分支拉取更新
- 保持 PR 小而专注
- 及时合并已审核的 PR
- 避免长时间在分支上开发
- 使用 `.gitattributes` 标记容易冲突的文件
